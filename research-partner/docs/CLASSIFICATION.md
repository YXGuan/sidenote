# Automatic categorization

OpenAlex-indexed items now use the full work API record's `topics` and `keywords`
for their displayed automatic classification, including library filters and charts.
Keywords are independent labels; they are not assigned invented parent topics.
Manual classification corrections continue to take precedence. Local taxonomy rules
remain the fallback for items without an OpenAlex record, and still identify source
format independently. Empty topic/keyword lists in a matched work remain empty.

The complete singleton JSON response is stored in `vault/openalex/W<ID>.json` and
included in snapshots/restores. Topic/keyword IDs, scores, and topic hierarchy are
also retained in metadata. The API URL and retrieval time are recorded. Bibliographic
identity corrections invalidate old OpenAlex labels without deleting raw API evidence.
For the Work API shape, see [OpenAlex attributes](https://help.openalex.org/data/works/attributes/).

Backfill already indexed items without model calls or new title searches:

```sh
./research-partner/notes cache-openalex
# Explicitly refresh API records cached within the last seven days:
./research-partner/notes cache-openalex --force
```

The normal research enrichment path also caches singleton responses for new matches.
Research index links include arXiv whenever a valid identifier is available from
the source URL, captured metadata, Semantic Scholar, or OpenAlex repository locations.
Crossref/Zotero remain separate optional citation extraction tools.

**All active topics and labels:** [complete catalog](TAXONOMY.md), including every
local matching phrase and the distinction between subjects, auto tags and manual
tags. For the newer sycophancy example, see the [hierarchical classification
diagnostic and next steps](CLASSIFICATION-EXPLORATION.md). Its proposed hierarchy
is experimental and does not replace the active two-level schema.

The current version uses a [local subject hierarchy](../research_notes/taxonomy.json), separates format from subject, and includes scholarly enrichment and optional summaries. See the [redesign guide and real-public-paper Luna trial](LIBRARY-REDESIGN.md). The invented-example results below are historical smoke checks from the earlier taxonomy.

New users get automatic local categorization after their first import, subsequent
imports, browser metadata captures, and mirrored annotation saves. Setup requires
no model account or model download. Install the small NLP dependencies described
in the [backend guide](../README.md) for automatic collections. Every saved page is attempted; insufficient
evidence remains unknown. Bibliographic fields are observed metadata, never
generated by a classifier. Manual tags, collections, ratings, and annotation
reactions are independent of all classification results.

## Coverage and general readiness

The production fallback lives in [`research_notes/taxonomy.json`](../research_notes/taxonomy.json),
with 15 top-level subjects and 27 subtopics. [`TAXONOMY.md`](TAXONOMY.md) is a
generated readable catalog; `experiments/hierarchy-taxonomy.json` is an experiment,
not the active vocabulary. Regenerate the catalog with
`python3 -B tools/render_taxonomy.py` from the repository root.

**It is broad in outline, but not yet general enough for a public default.**
Computer science emphasizes language models and AI, research has dedicated
methods/communication labels, and religion's two subtopics are Christian.
Economics, arts, and business have no subtopics. History, law, geography,
engineering, travel, food, home, and several religious traditions lack dedicated
coverage. English phrase rules do not establish multilingual quality. The
eight-example benchmark measures a smoke fixture, not general classification
accuracy or fairness across subjects.

There are also two vocabularies in displayed data: enriched papers use OpenAlex
topics/flat keywords, while other pages fall back to these local labels. They
should retain their provenance rather than be treated as interchangeable levels
of one universal tree. Format (paper, blog, video, etc.) remains independent of
subject, and unknown is a valid result.

Before broadening the default, evaluate a reviewed cross-domain and multilingual
sample, measure coverage/false positives/abstention per domain, introduce optional
subject packs and editable labels, and version migrations so manual corrections
and older derived results remain understandable. Avoid simply adding generic
keywords: words such as “model,” “portfolio,” and “treatment” are ambiguous.
The [public roadmap](../../README.md#future-plan-from-research-workspace-to-everyday-reading)
keeps these tasks separate from the current research-focused implementation.

## Current implementation

The fallback provider is `local`: URL/citation evidence identifies source types,
and a small English phrase vocabulary assigns multiple topics and parent-linked
subtopics. It runs entirely in Python with no third-party dependencies, network
calls, or subprocesses. Results identify their provider as `local-rules`. This is
a conservative baseline, not semantic understanding. It can miss synonyms,
languages, unfamiliar domains, and topics outside its vocabulary. A generic word
such as “model” does not establish AI, and unknown evidence stays unknown.

The optional Codex provider explicitly runs **`gpt-6-luna`** with **low** reasoning
effort, structured output, and the existing isolated headless CLI boundary. It
never silently selects the user's global Codex model. That exact model ID and its
structured-output support are documented by [OpenAI](https://developers.openai.com/api/docs/models/gpt-6-luna).
The CLI supports explicit [model/config overrides](https://learn.chatgpt.com/docs/config-file/config-reference).
This workspace includes the verified official CLI v0.163.0 in ignored
`.local-tools/`; the original system CLI remains unchanged. Recreate it with the
command in [the backend guide](../README.md). Model availability still depends
on the signed-in account. Failures preserve
existing records and manual edits; they do not switch to a more expensive model.

From the workspace root:

```sh
# Show settings. New vaults default to local + automatic.
./research-partner/notes categorization

# Organize all uncached pages entirely locally.
./research-partner/notes organize --provider local

# Disable automatic import/capture categorization; manual refresh still works.
./research-partner/notes categorization --automatic off

# Restore the local automatic default.
./research-partner/notes categorization --provider local --automatic on
```

The dashboard's **Categorize with** selector can run a one-off local or Codex
backfill. Only Codex shows a transfer confirmation: selected saved titles, URLs,
citation metadata, highlights, comments, and personal notes go to the signed-in
Codex service. Local categorization needs no transfer approval.

For users who explicitly choose ongoing Codex categorization:

```sh
./research-partner/notes categorization --provider codex --automatic on --allow-private-context
```

That stores a preference for this vault and authorizes future imports/captures,
so there is no repeated per-paper approval. Switching back to local revokes that
ongoing Codex preference. A one-off CLI Codex run uses
`organize --provider codex --allow-private-context`. To override the model for one
invocation, prefix it with `NOTES_CODEX_MODEL=<model-id>`; the default remains Luna.
The default daily annotation backup works without Codex and remains successful
if categorization fails. Changed provider/model/input invalidates its cache.

## Automatic collections with local NLP

Automatic collections are independent of subject classification. They use
workspace-local **NLTK 3.10.4** (Treebank tokenization plus English question
patterns) and **VADER 3.3.2** (sentiment with a bundled lexicon). No runtime network
access or model/corpus download is required. These are English-oriented
heuristics, not a trained question classifier or evidence of personal preference.

- **Liked (Auto)**: personal comments with VADER compound score at least 0.35.
  There must be more positive than negative comments. Source highlights, Markdown
  blockquotes/code, and question-only sentences do not count as liking. Explicit
  page or annotation dislikes take precedence. Manual Likes remains separate.
- **Questions (Auto)**: comments or highlighted passages containing question
  punctuation, interrogative token patterns, or phrases such as “I wonder whether.”
  URLs/code alone do not create question matches.
- **Visit Often**: at least three recorded visits in the last 30 UTC calendar days,
  sorted by that rolling count. Saved-page loads/tab returns are tracked by the
  updated extension; older counts were sidebar captures. Five-minute deduplication
  prevents reloads and opening the sidebar from counting repeatedly.

Membership is derived on each library read and after note edits, without writing
inferred reactions or automatic IDs into manual groups. The library refreshes on
focus and every 30 seconds while visible. Existing notes are included immediately.

References: [NLTK tokenizer](https://www.nltk.org/api/nltk.tokenize.treebank.html),
[VADER scoring](https://github.com/cjhutto/vaderSentiment#about-the-scoring), and
[Chrome tab events](https://developer.chrome.com/docs/extensions/reference/api/tabs).

## Local library assessment

These are different building blocks, not interchangeable ready-made organizers.
No additional NLP package or weights have been installed in the user's global
Python environment.

| Library | Useful role | Limits for this product | Decision |
| --- | --- | --- | --- |
| [SentenceTransformers](https://www.sbert.net/docs/sentence_transformer/usage/semantic_textual_similarity.html) | Embed a title/abstract and taxonomy descriptions; match by similarity; reuse embeddings for search/recommendations | Similarity needs a calibrated threshold and abstention; a fixed label set does not discover a reliable hierarchy | Best next local experiment. A runnable CPU adapter is included in the synthetic benchmark. |
| [Gensim](https://radimrehurek.com/gensim/models/ldamodel.html) | LDA discovers latent word distributions across a corpus | Discovered topics need naming and alignment; results need not match the user's stable categories or hierarchy | Consider later for corpus exploration, not the initial per-page router. |
| [NLTK](https://www.nltk.org/book/ch06.html) | Tokenization and small feature-based supervised classifiers | Requires feature design and labeled training examples for this taxonomy; not an out-of-the-box semantic classifier | In use for automatic question collections; subject classification still uses custom rules. |
| [spaCy](https://spacy.io/api/textcategorizer) | Trainable whole-document classification; `textcat_multilabel` matches the multiple-topic requirement | Needs labeled examples for our categories; extracted person/organization mentions do not establish authorship/affiliation | Consider for a trained local classifier and entity candidates with source evidence. |
| [Hugging Face Transformers](https://huggingface.co/docs/transformers/en/main_classes/pipelines#transformers.ZeroShotClassificationPipeline) | An NLI zero-shot classification pipeline can score supplied labels and support multiple labels | Model-specific download/runtime/license requirements; scores still require evaluation and thresholds | Compare a small NLI model against embeddings and Luna before choosing production weights. |

My recommendation is to keep the inexpensive rule baseline, evaluate local
embeddings next, and reserve optional Luna calls for reviewed ambiguous cases.
This is an engineering judgment, not a measured accuracy claim. Production does
not automatically send uncertain local pages to Codex.

## Reproducible exploration

The benchmark opens **no vault**. Its eight invented English examples cover
research, finance, sports, health, software, science, education, and abstention.

```sh
python3 -B research-partner/experiments/classification_benchmark.py --provider local
python3 -B research-partner/experiments/classification_benchmark.py --provider codex
```

An experimental SentenceTransformers adapter compares document vectors with topic
description vectors. It loads already-cached weights on CPU with
`local_files_only=True`, `trust_remote_code=False`, and hub offline mode. It does
not download a model or read private notes. Install the package and cache a chosen
model in a separate experiment environment before running:

```sh
python3 -B research-partner/experiments/classification_benchmark.py --provider sentence-transformers
```

Its initial similarity threshold is a prototype parameter, not a confidence
probability. It does not generate subtopics. The benchmark's type accuracy and
topic micro-F1 are smoke checks only: the examples deliberately overlap the rule
vocabulary and cannot establish real-world quality. Local model backends have
not been quality- or performance-tested here. Before switching production, use a
reviewed held-out sample, include unfamiliar/non-English/ambiguous pages, measure
multi-label and parent/subtopic accuracy, abstention, cold/warm latency, memory,
model size, and licensing. Keep bibliographic extraction a separate pipeline.

The recorded smoke results are in [results.json](../experiments/results.json):
local rules took 0.003 seconds, and Luna via CLI v0.163.0 took 7.712 seconds for
the eight invented pages. Both matched the expected link types; their topic
micro-F1 values were 1.0 and 0.947 respectively. These are unrepresentative smoke
results, including CLI startup/network time for Luna, and do not show that the
local rules are more accurate on real or unfamiliar pages.
